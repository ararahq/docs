## Como reportar bug

<Steps>
  <Step title="Confira se já não existe">
    Procure nas **Issues** do repositório correspondente antes de abrir. Bug duplicado é fechado apontando para o original.
  </Step>
  <Step title="Reproduza isolado">
    Snippet mínimo que reproduz o bug, sem código de produção inteiro.
  </Step>
  <Step title="Abra a issue">
    Inclua:
    - Versão do SDK, CLI ou MCP (ex: `@ararahq/sdk@1.8.1`)
    - Versão do runtime (Node 20, PHP 8.2 etc.)
    - Sistema operacional
    - Comportamento esperado vs observado
    - Snippet reproduzível e, se houver, o `error.code` e o `id` da mensagem (`ara_msg_...`)
  </Step>
</Steps>

<Warning>
  Nunca cole API Key, secret de webhook ou dados de clientes em issue. Falha de segurança vai direto para [suporte@ararahq.com](mailto:suporte@ararahq.com), não para issue pública.
</Warning>

Problema com a API em si, e não com um SDK, também vai para [suporte@ararahq.com](mailto:suporte@ararahq.com).

## Como sugerir melhoria

Abra uma issue descrevendo:

- O problema que você está tentando resolver
- A solução que você imagina
- Alternativas consideradas
- Quem se beneficia

Mudanças pequenas (helper, validação, correção de doc) podem ir direto em PR. Mudanças grandes (recurso novo, mudança de interface pública) precisam de alinhamento na issue antes.

## Pull Requests

### Antes de codar

- Abra ou comente na issue para alinhar a abordagem
- Avise que vai pegar a tarefa para evitar trabalho duplicado
- Fork, branch (`feat/xxx` ou `fix/xxx`) e PR

### O que esperamos

| Critério | Requisito |
|---|---|
| **Testes** | Funcionalidade nova vem com teste. Bug fix vem com teste que falha antes do fix. |
| **Checks do repositório** | Rode o que o repositório usa antes de abrir o PR. Veja a tabela abaixo. |
| **Commit message** | `tipo(escopo): descrição`, sem emojis (ex: `feat(messages): add interactive payload type`) |
| **CHANGELOG** | Se o repositório tem changelog, adicione a entrada |
| **Docs** | Se mudou interface pública, atualize o README |

| Repositório | Comandos |
|---|---|
| `arara-node-sdk` | `npm test` e `npm run build` |
| `arara-python-sdk` | `ruff check .`, `mypy` e `pytest` |
| `arara-php-sdk` | `composer check` (PHPStan + PHPUnit) |
| `arara-java-sdk` | `./gradlew build` |
| `arara-go-sdk` | `go vet ./...` e `go test ./...` |
| `cli` | `make ci` (vet, lint, race e cobertura). Detalhes no `CONTRIBUTING.md` do repositório |
| `mcp` | `npm run check` (format, lint, typecheck, testes e build) |

### Tamanho do PR

Pequeno e focado. PR grande fica difícil de revisar: divida em série.

## Documentação

Esta página e todas as outras desta doc vivem em [github.com/ararahq/docs](https://github.com/ararahq/docs), construídas com Mintlify.

Para rodar localmente:

```bash
git clone https://github.com/ararahq/docs
cd docs
npm i -g mint
mint dev  # preview em http://localhost:3000
```

Edite o `.mdx` correspondente, confira o preview e abra o PR.

### Padrões

- **Tom**: direto, sem hype, honesto sobre limitações
- **Slugs**: inglês curto (`/concepts/whatsapp`, não `/conceitos/`)
- **Snippets**: validados contra a API real, nunca inventados
- **Frontmatter**: `title` e `description` obrigatórios; `keywords` recomendado
- **Idioma**: pt-BR, mantendo termos técnicos consolidados (webhook, payload, retry)

## Conduta

- **Respeito**: assuma boa-fé. Critique o código, não a pessoa.
- **Inclusão**: sem comentários discriminatórios. Tolerância zero.
- **Construtividade**: "isso não funciona" não ajuda. "Isso não funciona porque X, sugiro Y" ajuda.

Para reportar violação, escreva para [suporte@ararahq.com](mailto:suporte@ararahq.com).

Agência que opera WhatsApp para vários clientes precisa de isolamento: a chave do cliente A não pode tocar dados do cliente B, e cada cliente paga o próprio consumo.

Na Arara, a unidade de isolamento é a **organização**. Número, templates, contatos, conversas, campanhas, webhook, Brain e carteira pertencem à organização.

## Como a Arara organiza acesso

- Cada organização é uma conta separada, com faturamento próprio.
- Cada **usuário** (e-mail) pertence a **uma organização por vez**.
- A chave de API pertence ao usuário que a criou e age na organização desse usuário.
- Não existe troca de organização por API nem painel com várias organizações sob um mesmo login.

Por isso o modelo recomendado é **uma organização por cliente, com um usuário da agência em cada uma**.

<Warning>
  Não aceite, com o mesmo e-mail, convites de organizações diferentes. Aceitar um convite **move** o usuário para a organização que convidou, e as chaves de API desse usuário passam a agir nela. Use um e-mail por cliente (por exemplo `operacao+clientex@suaagencia.com`).
</Warning>

## Setup por cliente

<Steps>
  <Step title="Cliente cria a conta">
    O cliente cria a conta Arara com os dados dele e conecta o número. Ele continua dono da organização (`OWNER`) e dos dados.
  </Step>
  <Step title="Cliente convida a agência">
    Pelo dashboard ou pela API, com um e-mail exclusivo da agência para esse cliente:
    ```bash
    curl -X POST https://api.ararahq.com/v1/team/invitations \
      -H "Authorization: Bearer ara_live_chave_do_cliente" \
      -H "Content-Type: application/json" \
      -d '{ "emails": ["operacao+clientex@suaagencia.com"], "role": "ADMIN" }'
    ```
    Papéis: `ADMIN`, `DEVELOPER`, `AGENT`, `BILLING`, `VIEWER`. `OWNER` não é atribuído por convite, só por transferência. Só `OWNER` e `ADMIN` convidam.
  </Step>
  <Step title="Agência entra com esse e-mail">
    Quem entra pela primeira vez com um e-mail que tem convite pendente já cai na organização do cliente, com o papel do convite.
  </Step>
  <Step title="Agência cria a chave de API">
    Logado nessa organização, crie a chave pelo dashboard (**API Keys**). Criação e gestão de chaves exigem sessão do dashboard de um `OWNER` ou `ADMIN` (`VIEWER` só cria chave restrita a envio); chamada autenticada com chave de API recebe 403. A chave completa só aparece na criação: guarde no seu cofre de segredos.
  </Step>
</Steps>

## Uma instância de SDK por cliente

```typescript
import { NodeSDK, type SendMessageRequest } from '@ararahq/sdk';

const clients = new Map<string, NodeSDK>([
  ['cliente-x', new NodeSDK({ apiKey: process.env.ARARA_KEY_CLIENTE_X! })],
  ['cliente-y', new NodeSDK({ apiKey: process.env.ARARA_KEY_CLIENTE_Y! })],
]);

export async function sendFor(clientId: string, payload: SendMessageRequest, idempotencyKey: string) {
  const sdk = clients.get(clientId);
  if (!sdk) throw new Error(`Cliente ${clientId} não configurado`);
  return sdk.messages.send(payload, { idempotencyKey });
}
```

Com muitos clientes, guarde as chaves criptografadas no seu banco ou num gerenciador de segredos, nunca no código nem no frontend.

Cada organização tem o próprio webhook e o próprio secret (`GET /organizations/me/webhook` com a chave daquele cliente). No seu endpoint, use o `organizationId` do payload para saber de qual cliente é o evento, e valide a assinatura com o secret certo.

## CLI com profiles

Cada profile guarda a própria credencial:

```bash
arara profile add cliente-x
arara login --profile cliente-x

arara profile add cliente-y
arara login --profile cliente-y

arara profile list
arara profile switch cliente-x
arara send --to +5511999999999 --template ola_mundo --vars "João"

# Ou sem trocar o profile ativo
arara send --profile cliente-y --to +5511999999999 --template ola_mundo --vars "Maria"
```

`arara org list` e `arara org use` existem, mas não trocam a credencial: a chave continua agindo na organização do usuário. Para trocar de cliente, troque de profile. Ver [CLI](/cli).

## Isolamento

| Dado | Escopo |
|---|---|
| Número de WhatsApp | Organização |
| Templates | Organização |
| Contatos, conversas, opt-outs | Organização |
| Campanhas e automações | Organização |
| Webhook (URL e secret) | Organização |
| Base de conhecimento do Brain | Organização |
| Carteira e faturamento | Organização |
| Chaves de API | Usuário, agindo na organização dele |

## Segurança

### Uma chave por cliente

Se a chave de um cliente vazar, revogue só ela (`DELETE /v1/api-keys/{id}` pela sessão do dashboard, ou em **API Keys**). As outras organizações não são afetadas.

### Restrinja a chave

Na criação ou edição da chave dá para definir:

- `ipAllowlist`: IPs ou faixas CIDR separados por vírgula. Chamada de fora da lista é recusada. Depende do plano.
- `permissions` e `scope`: o que a chave pode fazer.
- `dailySendLimit`: teto de envios por dia.
- `expiresAt`: validade.

### Auditoria

- `GET /v1/api-keys/{id}/events`: histórico da chave (criada, revogada, rotacionada, mudança de escopo ou IP), com `actorUserId` e data.
- `GET /v1/api-keys/{id}/stats`: volume de chamadas e taxa de sucesso em 7 e 30 dias.
- `GET /v1/team/audit-log`: eventos do time (convites, mudanças de papel, remoções).

`events` e `stats` exigem sessão do dashboard de `OWNER` ou `ADMIN` (não aceitam chave de API). O audit log do time exige `OWNER` ou `ADMIN`.

## Faturamento

Cada organização tem carteira e assinatura próprias. O cliente paga o consumo dele diretamente. A cobrança da agência pelo serviço é feita por fora da Arara.

Para revenda sob a sua marca, fale com [contato@ararahq.com](mailto:contato@ararahq.com).

## Métricas por cliente

Não há visão agregada de várias organizações. Consulte cada uma com a chave dela, por exemplo `GET /v1/campaigns`, `GET /v1/contacts/stats` e `GET /v1/recovery/stats`, e consolide do seu lado.

## Offboarding

Quando um cliente sai da agência:

1. O cliente remove o usuário da agência em **Time** (ou `DELETE /v1/team/members/{id}`). A remoção revoga todas as chaves de API desse usuário.
2. Apague a chave e o profile do CLI (`arara profile remove cliente-x`) do seu lado.
3. Se o cliente pedir, exporte os contatos (`GET /v1/contacts/export`) antes da saída.

## Checklist de produção

- [ ] Uma organização por cliente, criada pelo próprio cliente
- [ ] Um e-mail da agência por cliente; nenhum e-mail aceitando convite de duas organizações
- [ ] Papel mínimo necessário no convite
- [ ] Uma chave por cliente, guardada em cofre de segredos
- [ ] `ipAllowlist` e `dailySendLimit` nas chaves de produção, quando o plano permitir
- [ ] Webhook de cada cliente validado com o secret daquela organização
- [ ] Profiles do CLI separados por cliente
- [ ] Processo de offboarding combinado com cada cliente

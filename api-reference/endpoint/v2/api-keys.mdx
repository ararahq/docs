As chaves são geridas **no painel**. As rotas `/v1/api-keys` são as que o próprio painel usa e só aceitam sessão de usuário com papel de Dono ou Admin (criar, listar e revogar também liberam o papel Leitor, para chaves de envio vinculadas).

<Warning>
  Chamar `/v1/api-keys` com uma API key responde `403 RESOURCE_FORBIDDEN`. Uma chave não cria, lista, rotaciona nem revoga chaves. Isso é intencional: uma chave vazada não consegue gerar outras.
</Warning>

## O que você configura na criação

| Campo | Descrição |
|---|---|
| Nome | Obrigatório. Descreva onde a chave roda (ex.: "backend-producao"). |
| Permissões | `READ`, `MESSAGES_SEND`, `TEMPLATES_WRITE`, `CAMPAIGNS_SEND`, `CONTACTS_WRITE`, `WEBHOOKS_MANAGE` ou `ADMIN`. Sem escolha, a chave nasce `ADMIN`. O que cada uma libera está em [Autenticação](/api-reference/authentication#permissões). |
| Expiração | Opcional. Depois da data a chave responde `401`. |
| IP allowlist | Opcional. IPs e CIDR IPv4 separados por vírgula. Exige plano com trilha de auditoria (`403 PLAN_FEATURE_LOCKED` sem ele). |
| Limite diário de envio | Opcional, de 1 a 1.000.000 mensagens por dia (UTC). Estourou: `429 SEND_RATE_LIMITED`. |
| Remetente e template vinculados | Opcional. Usado por chaves de disparo via webhook de parceiro; informe os dois juntos. |

O valor completo (`ara_live_...`) aparece **uma única vez**. A Arara guarda só o hash e os 4 últimos caracteres.

## Campos exibidos na listagem

| Campo | Descrição |
|---|---|
| `id` | UUID da chave. |
| `name` | Nome (`"Sem nome"` em chaves antigas). |
| `prefix` | Sempre `ara_`. |
| `lastFour` | Últimos 4 caracteres, para identificar sem expor. |
| `mode` | Sempre `LIVE`. |
| `scope` | Escopo legado (`READ`, `SEND`, `ADMIN`). |
| `permissions` | Permissões efetivas. |
| `dailySendLimit` / `dailySendCount` | Teto diário e quanto já foi usado hoje. |
| `createdAt`, `lastUsedAt`, `expiresAt`, `expired` | Datas de ciclo de vida. `lastUsedAt` é atualizado no máximo uma vez por minuto. |
| `ipAllowlist` | Allowlist configurada. |
| `rotatedFromId` | Chave de origem, quando veio de rotação. |
| `senderNumber`, `templateName` | Vínculo de webhook, quando houver. |

A listagem traz todas as chaves não revogadas da organização.

## Rotação

Rotacionar gera uma chave nova com as mesmas permissões, expiração, allowlist e limite, e **revoga a antiga no mesmo instante**. Não há janela de convivência. Para trocar sem downtime:

<Steps>
  <Step title="Crie uma segunda chave">
    Com as mesmas permissões da atual.
  </Step>
  <Step title="Publique a nova chave">
    Atualize a variável de ambiente e faça o deploy.
  </Step>
  <Step title="Revogue a antiga">
    Confirme no painel que a antiga parou de ser usada (`lastUsedAt`) e revogue.
  </Step>
</Steps>

## Auditoria

Cada chave guarda eventos de ciclo de vida: `CREATED`, `ROTATED`, `REVOKED`, `EXPIRED`, `SCOPE_CHANGED`, `IP_ALLOWLIST_CHANGED` e `CONFIG_CHANGED`, com o usuário que fez a ação. O painel também mostra o volume de requisições em 7 e 30 dias e a taxa de sucesso (2xx) em 30 dias.

## Segurança

- Nunca coloque a chave no frontend, em repositório ou em log.
- Use variável de ambiente ou cofre de segredos.
- Uma chave por serviço e por ambiente, com a menor permissão necessária.
- Revogue na hora quando suspeitar de vazamento ou quando alguém com acesso sair do time.
